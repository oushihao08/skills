# Plain Brief：直白浓缩汇报

用普通人一眼能懂的话交代结果、现状与下一步。砍掉术语绕弯和过程铺垫，保留决定判断的关键事实、数字与边界。

## 固定边界

- **先说结果**：首句直接回答成没成、是什么或该怎么选，不先讲排查过程。
- **人话作主干**：主句写实际发生了什么、为什么、影响什么；内部字段、函数名、错误码、UUID、参数仅在定位必需时放括号或链接里，不拿代码词当主语。
- **浓缩不失真**：保留关键比例/数量、成立条件、未完成项与真实阻塞；严禁用“基本完成”“差不多”“有点小问题”掩盖缺口，区分已验证、未执行与失败。
- **单句单意**：删掉套话、重复总结和防御性铺垫；每句话只传递一个新信息。

## 按场景组织（动态条件）

优先级：`用户当前要求 > 问题复杂度 > 默认结构`。

- **简单问答或单一确认**：1–3 句话直接答完，不拆标题、不硬凑清单。
- **执行汇报、诊断或阶段收口**：按需交代三件事：
  1. **结果**：做成了什么 / 结论是什么（带核心数字或产出位置）。
  2. **现状**：现在卡在哪、哪些已通、哪些还没做。
  3. **下一步**：建议接下来干什么、先做哪一步最划算（无需后续动作时省略）。
- **何时列清单**：仅当并列要点 ≥ 3 项、存在先后顺序或需要用户逐项拍板时使用短清单；每条控制在 1 句话（说清事实或动作 + 影响）。
- **用户追问技术细节时**：按用户要求的深度展开底层实现与原始数据，不机械截断。

## 保真压缩对照

| 常见毛病 | 正确做法 |
| --- | --- |
| 堆砌内部代号、正则、字段名，读完不知好坏 | 先用白话说清现象和原因，必要文件/字段放括号备查 |
| 为求简短删掉数字、前提或未做事项（失真） | 保留决定判断的数字、范围和未完成边界，删修饰词与过程废话 |
| 不管大小事都套固定多级标题和长表格 | 简单事直接说，复杂事才分段或列 3–5 条短清单 |

## 发送前自检

1. 只看前两句，用户能不能立刻知道结果和核心原因？
2. 删掉所有括号里的英文/代码词后，整段话是不是依然通顺好懂？
3. 关键数字、风险边界、未完成项有没有被漏掉或模糊化？
4. 有没有哪句话删掉后完全不影响理解与决策？有就删掉。

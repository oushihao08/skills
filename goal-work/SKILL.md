# Goal Work

执行 `/goal` 时用这些规则判断、开工和收尾。不要改 `/goal` 的命令、状态和完成机制。

## 固定边界

这三条先于流程和文档格式：

- **第一性原理**：从目标、已证实的事实和必要约束出发。先分清已证实、假设和未知。修问题先查原因。新建先明确必要能力。
- **最短路径**：在完成目标、保持正确和满足约束的前提下，用必要步骤最少的做法。能直接完成就不加中间步骤。
- **不要过度设计**：只做这次目标及其已确认的必要能力。不为假想需求加抽象、层级、配置或流程。

代码：

- 沿用当前仓库已有的写法和模块。只改这次目标要改的部分。
- 不为复用、解耦或模块化提前拆分。
- 后端行为变化要有针对该行为的单元测试，并运行这些测试。
- 前端不写测试。

给 agent 读的产物用 `writing-prompt` [$writing-prompt](/Users/jack/.agents/skills/writing-prompt/SKILL.md) 。范围是 agent 提示词、skill、agent 知识库，以及要求 agent 读取并遵守的文档。这是写法规范，不是完成步骤。给人看的任务说明不用 `writing-prompt`。

## 由这次目标决定

开工前先确定：

- 这次业务要达成什么，现有行为是什么。
- 相关文件各自负责什么，和哪些文件有调用、数据或页面上的挂靠。
- 改动落在现有设计的哪一处。设计不够时，只补这次目标必要的那一处。

计划说明的内容由这次目标决定。不规定固定章节，不为模板拆成多份文档；执行证据按下方Trace规则归档。

一步就能完成，且完成标准已经写明时，不另写清单和验收。目标有多个步骤，或完成标准还没写明时，开工前必须写出：

- **任务清单**：还要做的步骤。
- **验收标准**：做到什么算完成；每一条用什么事实判断；哪些结果这次不验收。

写进这次目标已经在用的记录。不新开文件。没有记录时，写在用户给出这次目标的同一处。

## 执行观察

执行中存在多阶段依赖、重复操作、长等待或编排瓶颈时，使用 [$pace](/Users/jack/.codex/skills/pace/SKILL.md) 优化剩余路径、顺序与并行安排；沿用本次目标和清单，不重复规划。简单任务直接执行，不为启用提效流程增加步骤。

多阶段目标的执行与恢复使用 [$trace](/Users/jack/.codex/skills/trace/SKILL.md)：关联已有计划item，记录各次尝试、问题、阶段成果和证据，在业务项目的`执行观察/`中维护同一目标的记录。这里只引用计划，不复制另一套计划；不改变`/goal`机制、业务步骤或授权。已有等效记录时按Trace约定接续，不另开重复台账。

## 完成

完成前使用开工时写出的验收标准。开工时没有写，就在完成前补写：做到什么算完成，每一条用什么事实判断，哪些结果这次不验收。内容只来自这次目标。写进已有记录；没有记录时，写在用户给出这次目标的同一处。

按 `verification-before-completion` 核对。证据必须来自这次执行。证据对上才声称完成。后端行为的验收包含运行对应单元测试。前端不把测试当作验收。

完成后做两件事：

- 删除这次任务的临时执行文档，例如临时计划。不删除本次目标原有记录、仓库原有文档或Trace留下的追溯记录与必要证据。
- 先用短文总结这次做了什么，再用一张表列全。短文只写结果，不写过程。表每件事一行，覆盖全部改动。列：事项、结果。
